# FAIL-0004 -- IEC 62368-1 only triggers on mains power, not adapter/USB-powered ICT equipment

Date: 2026-09-25

## What happened

`standards.toml`'s `iec-62368-1` row's `applies_if` was
`[{field = "power_source", op = "in", value = "mains"}]`. The `"in"` predicate checks
`isinstance(profile_field, list) and value in profile_field` -- so it only ever matched a
profile whose `power_source` was literally a *list* containing the string `"mains"`
(`power_source = ["mains"]`); a profile with `power_source = "mains"` (a bare string, the
form every worked example used) or `power_source = "usb"` / `"external_adapter"` never
matched at all. In practice this meant IEC 62368-1 (audio/video, IT and communications
equipment safety -- exactly the standard that applies to a USB- or adapter-powered sensor)
almost never triggered, for almost any real profile.

## Five whys

1. Why did it happen? The predicate was written as `op = "in"` with a scalar `value =
   "mains"`, but `"in"`'s own semantics (`_op_matches`) check that the *profile* field is a
   list containing the value -- the row's author had the direction backwards (wanted "does
   power_source contain mains", wrote a predicate that checks "is power_source a list that
   contains the literal string mains").
2. Why wasn't this caught when the row was written? There was no test that exercised
   `iec-62368-1`'s `applies_if` against a realistic profile and asserted it actually
   matched -- `applicable_standards()` had general tests, but no seeded-wrong case for any
   individual standard's trigger condition.
3. Why didn't the trigger's narrowness (mains-only) get questioned independently of the bug?
   R5b's original research (`iec-62368-1` row `trigger` text) already said "Any mains- or
   battery-powered AV/ICT product ... sensors with a mains adapter," which is broader than
   "mains" alone -- but the `applies_if` predicate was never checked against the row's own
   stated trigger text for consistency.
4. Why wasn't the predicate bug found by manual review? `power_source` accepts several
   forms in practice (a bare string, a list, or a legacy `"battery_and_mains"` string) and
   the review that added `normalise_power_source()` (splitting `"_and_"` strings into a
   list) happened at a different time from the `iec-62368-1` row's own predicate logic --
   the two were never re-verified together against the same test profile.
5. Why (root cause)? A trigger condition's correctness was judged by reading it, not by
   running it against a concrete profile and checking the result -- exactly the kind of
   "looks right" mistake a seeded-wrong test with an assertion on the actual match result
   would have caught immediately.

## New mechanism

- Mechanism: `verify.py` now normalises `power_source` into a list unconditionally
  (`normalise_power_source()`, called before predicates run) and adds `"any_in"` as a
  predicate op (`isinstance(actual, list) and isinstance(value, list) and bool(set(actual)
  & set(value))`). The `iec-62368-1` row's `applies_if` is now
  `[{field = "power_source", op = "any_in", value = ["mains", "external_adapter", "usb",
  "battery"]}, {field = "category", op = "not_one_of", value = ["medical", "automotive"]}]`
  -- matching R5f's confirmation that the IEC abstract's scope names no power-source
  condition at all (just "electrical and electronic equipment ... not exceeding 600 V"), so
  adapter- and USB-powered ICT equipment is squarely in scope, not just equipment plugged
  directly into mains. A `profile.power_source_valid` measurement also FAILs an unknown or
  empty `power_source` value (which would otherwise silently map no power-dependent
  standard at all).
- File(s): `plugins/forge/skills/mapping-compliance/scripts/verify.py`
  (`normalise_power_source`, `_op_matches`'s `"any_in"` branch,
  `profile.power_source_valid`), `plugins/forge/skills/mapping-compliance/references/standards.toml`
  (`iec-62368-1` `applies_if`, `trigger` text updated per R5f),
  `docs/research/R5f-compliance-data-gaps.md` (the scope-sentence sourcing),
  `plugins/forge/tests/systems/test_mapping_compliance.py`
  (`test_iec_62368_1_applies_to_adapter_and_usb_powered_ict_not_just_mains`).

## Proof it catches the original failure

Reproduced directly against the ORIGINAL (commit `7a7bfa5`) `standards.toml`/`verify.py`
and the current (fixed) version, on the identical profile
(`power_source = "usb"`, no radio, US market):

- **Before the fix**: `[PASS]`, exit 0, `notes: "1 standard(s) matched: ['fcc-part15']"` --
  `iec-62368-1` never appears; `compliance/standards-map.md` has no `iec-62368-1` section
  at all for a USB-powered ICT product.
- **After the fix**: `[PASS]`, exit 0, `notes: "2 standard(s) matched: ['iec-62368-1',
  'fcc-part15']"` -- `compliance/standards-map.md` now includes an `iec-62368-1` section
  with its edition, the R5f-sourced scope citation, and the "needs a qualified human"
  note.
- Regression test:
  `test_iec_62368_1_applies_to_adapter_and_usb_powered_ict_not_just_mains` (asserts
  `iec-62368-1` appears in `standards-map.md` for a `["usb", "external_adapter"]` power
  source).
