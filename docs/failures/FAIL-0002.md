# FAIL-0002 -- mapping-compliance passes a radio profile that contradicts the requirements

Date: 2026-09-25

## What happened

`compliance/product-profile.toml`'s `radios` field and `requirements/**/*.md` were never
cross-checked against each other. Two independent, both-wrong scenarios passed silently:

1. A requirement named a radio (e.g. "the device shall pair over Bluetooth Low Energy
   (BLE)") that the profile's `radios` list never mentioned -- so no Bluetooth EMC or
   spectrum standard was ever mapped for a radio the product actually has.
2. The profile's `radios` list claimed a radio (e.g. `radar_60ghz`) that no requirement or
   `params.toml` entry ever named -- an invented radio, mapping standards for hardware that
   may not exist.

Review #2's addendum sweep (K1) reproduced both directions directly against a profile/
requirements pair seeded with each mismatch: PASS in both cases.

## Five whys

1. Why did it happen? `verify.py`'s `run()` read `compliance/product-profile.toml` and
   `standards.toml` only -- it never opened `requirements/` or `params/params.toml` at all,
   so the profile's `radios` field was trusted as ground truth with nothing to check it
   against.
2. Why was the profile trusted as ground truth? The skill's job was framed as "map this
   profile to standards," not "confirm this profile matches the rest of the project" -- the
   profile was treated as an input, like a form filled in by a human, rather than a claim
   that needed corroboration from the requirements a systems engineer actually wrote.
3. Why didn't a wrong `radios` list get caught downstream? No other Forge check reads
   `compliance/product-profile.toml`, and `tracing-requirements`/`writing-requirements` know
   nothing about the compliance domain's vocabulary -- there was no seam where the two
   ever met.
4. Why wasn't this designed in from the start? The original brief's compliance mapping was
   scoped as "given a profile, produce a standards list," and the profile-authoring step
   (a human or agent filling in `radios`) was assumed reliable without a cross-check,
   the same optimistic-input assumption FAIL-0001's market code had.
5. Why (root cause)? Forge's general rule -- every claim needs an independent, machine-
   checkable corroboration, never just a human's say-so -- wasn't yet applied to the
   compliance profile itself. A `radios` entry is exactly the kind of self-reported field
   that needs a second, independent source (here: the requirements text) before it's
   trusted enough to drive which regulations get mapped.

## New mechanism

- Mechanism: `verify.py` now cross-checks the profile against `requirements/**/*.md` and
  `params/params.toml` in both directions, using `standards.toml`'s new `[[radio_family]]`
  regex patterns (`wifi`, `bluetooth`, `ieee802154`, `radar` -- deliberately narrow, e.g.
  `\bBLE\b` upper-case-only so "table"/"cable" never match, "Thread" excluded so screw
  threads never match):
  - `radios.requirements_named_radio_missing` FAILs when a family is named in the
    requirements/params text but no profile `radios` id of that family (and no
    `[radios_excluded]` note) covers it.
  - `radios.profile_radio_untraced` FAILs when the profile lists a radio family that no
    requirements/params text names at all.
  - `radios.cross_check_inputs_present` FAILs when there is nothing to cross-check against
    (no `requirements/` and no `params/params.toml`), so a missing/invented radio can never
    pass merely because the corroborating source doesn't exist yet.
  - `radios.radios_declared` / `radios.has_radio_consistent` catch `has_radio = true` with
    no `radios` list, and `has_radio` disagreeing with whether `radios` is non-empty.
- File(s): `plugins/forge/skills/mapping-compliance/scripts/verify.py`
  (`radio_families`, `named_radio_families`, the `radios.*` measurements),
  `plugins/forge/skills/mapping-compliance/references/standards.toml` (`[[radio]]`,
  `[[radio_family]]` tables), `plugins/forge/tests/systems/test_mapping_compliance.py`
  (`test_radio_named_in_requirements_but_missing_from_profile_fails`,
  `test_radio_in_profile_but_untraced_in_requirements_fails`,
  `test_radio_traced_both_ways_passes`).

## Proof it catches the original failure

Reproduced directly against the ORIGINAL `mapping-compliance/scripts/verify.py`
(commit `7a7bfa5`, the exact commit review #2's addendum audited -- unchanged from the
Phase 3 build for this skill), which had no `radios` field handling and no cross-check code
path at all, versus the current (fixed) version, on the same two seeded profile/requirements
pairs:

- **Direction 1** (`has_radio = false`, no `radios`; `requirements.md` names Bluetooth LE):
  - Before: `[PASS]`, exit 0, `notes: "0 standard(s) matched: []"`.
  - After: `[FAIL]`, exit 1 -- `radios.requirements_named_radio_missing` = `"bluetooth"` vs
    `{"equals": ""}`, `pass: false`, remediation names the missing family, the file:line it
    was first found at (`requirements/requirements.md:2`), and the valid radio ids to add.
- **Direction 2** (`radios = ["wifi_2g4"]`; `requirements.md` names only mechanical drop
  testing, no radio at all):
  - Before: `[PASS]`, exit 0.
  - After: `[FAIL]`, exit 1 -- `radios.profile_radio_untraced` = `"wifi"` vs
    `{"equals": ""}`, `pass: false`.
- Regression tests:
  `test_radio_named_in_requirements_but_missing_from_profile_fails`,
  `test_radio_in_profile_but_untraced_in_requirements_fails` (both FAIL cases, assert the
  specific measurement name and value), `test_radio_traced_both_ways_passes` (PASS case).
