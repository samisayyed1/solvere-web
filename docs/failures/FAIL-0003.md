# FAIL-0003 -- standards.toml lacks UK, RED core, radio EMC and radio spectrum rows

Date: 2026-09-25

## What happened

`standards.toml` had no UK-specific rows (UKCA route, Radio Equipment Regulations 2017,
UK EMC Regulations 2016, PSTI), no EU RED Article 3 core essential-requirements rows
(health and safety, EMC, spectrum, separate from the already-present `eu-red-cyber`
cybersecurity delegated act), and no harmonised radio-EMC or spectrum standards for the
2.4 GHz radios or 60 GHz radar (EN 301 489-1/-17/-3, EN 300 328, the EN 305 550 series, FCC
15.247/15.255, ISED RSS-247/RSS-210). A product with a UK market and a 2.4 GHz radio mapped
none of these -- `mapping-compliance` ran clean with a materially incomplete standards list,
and nothing in the check would ever fail to reflect that gap, because a missing *row* has
no measurement to fail.

## Five whys

1. Why did it happen? `standards.toml` was built from `docs/research/R5a`, `R5b` and `R5e`
   (Phase 3's original research pass), and none of those files researched the UK regime,
   RED's own Article 3 core text, or the specific harmonised EN/FCC/RSS radio standards --
   the data file could only be as complete as the research that had been done for it.
2. Why didn't the research cover them? R5a/R5b/R5e focused on general product-safety and
   cybersecurity standards (62368-1, RoHS, REACH, CRA, EN 303 645); the brief's example
   products (a UK-market radio sensor with 2.4 GHz Wi-Fi/BLE and an optional 60 GHz radar)
   weren't yet the driving scenario when that research was scoped.
3. Why wasn't the gap caught by a check? There is no check that can verify "the data file
   contains every standard that legally applies" -- that's an open-world fact about
   regulation, not something derivable from the repo's own contents. The only mechanism
   available is: research it, cite it, add the rows, and rely on `data.rows_sourced` (which
   already existed) to make sure whatever rows ARE added are properly sourced.
4. Why wasn't the gap noticed sooner? Every profile tested against `mapping-compliance`
   before this used US/EU/CA markets with the generic (already-present) standards; nothing
   exercised a UK profile with a 2.4 GHz radio or a 60 GHz radar until the review #2
   addendum sweep (K1) specifically probed for it.
5. Why (root cause)? A standards-mapping tool is only as complete as its data file, and the
   data file's completeness was never itself tracked as a requirement with acceptance
   criteria -- there was no explicit "the UK/RED-core/radio-EMC/spectrum rows are a known
   gap, tracked, and closed with sourced citations" until this failure made it one.

## New mechanism

- Mechanism: `docs/research/R5f-compliance-data-gaps.md` researches and sources (each row
  tagged `[V]` verified on the issuing body's own page/document with URL and access date, or
  `[U]` unverified because the primary source could not be read in this session) the UK
  regime (UKCA route, RER 2017 + its GB designated-standards list, EMC Regs 2016, PSTI),
  the EU RED Article 3 core (3(1)(a) safety, 3(1)(b) EMC, 3(2) spectrum), ETSI EN 301 489-1/
  -17/-3, EN 300 328, the EN 305 550 (60 GHz radar) series, FCC 15.247/15.255, and ISED
  RSS-210 Annex J -- `standards.toml`'s existing `data.rows_sourced` check enforces every
  R5f row carries its tag, `source_url` and `human_confirms_applicability = true`, or the
  whole check FAILs.
- File(s): `docs/research/R5f-compliance-data-gaps.md`,
  `plugins/forge/skills/mapping-compliance/references/standards.toml` (new `[[standard]]`
  rows `uk-ukca-route`, `uk-rer-2017`, `uk-emc-2016`, `uk-psti`, `eu-red-3-1-a`,
  `eu-red-3-1-b`, `eu-red-3-2`, `en-301-489-1`, `en-301-489-17`, `en-301-489-3`,
  `en-300-328`, `en-305-550-radar-60ghz`, `fcc-15-247`, `fcc-15-255`, `ised-rss-247`,
  `ised-rss-210`), `plugins/forge/tests/systems/test_mapping_compliance.py`
  (`test_uk_radio_product_maps_red_core_and_spectrum_and_emc_rows`).

## Proof it catches the original failure

Reproduced directly by running the ORIGINAL (commit `7a7bfa5`) `standards.toml` (18
`[[standard]]` rows, none UK/RED-core/radio-EMC/spectrum) and the current (30+ row, R5f-
sourced) file against the identical profile -- UK market, `wifi_2g4` radio, requirements
naming Wi-Fi:

- **Before the fix**: `[PASS]`, exit 0, `notes: "0 standard(s) matched: []"` -- a UK radio
  product with a fully valid, well-formed profile mapped *nothing at all*.
- **After the fix**: `[PASS]`, exit 0, `notes: "6 standard(s) matched: ['iec-62368-1',
  'uk-ukca-route', 'uk-rer-2017', 'en-301-489-1', 'en-301-489-17', 'en-300-328']"` --
  `compliance/standards-map.md` now names each row with its edition, why it applies, the
  R5f source and its `[V]`/`[U]` tag.
- Regression test: `test_uk_radio_product_maps_red_core_and_spectrum_and_emc_rows`
  (asserts `uk-rer-2017`, `en-301-489-1`, `en-301-489-17`, `en-300-328` all appear in
  `standards-map.md` for a UK `wifi_2g4` profile).

## Eval case

Not planted as a `compliance-cant-fail` review-findings defect (this is a data-completeness
gap in a shared reference file, not a per-project profile mistake an agent could seed into
one fixture); covered instead by the regression test above and by
`data.rows_sourced` (already-existing) continuing to enforce that every new R5f row stays
sourced.
